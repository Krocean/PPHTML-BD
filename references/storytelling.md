# 발표의 구조와 말투

덱을 **새로 만들 때** 읽는다. 템플릿과 테마는 겉모습이고, 듣는 사람이 결정을 내리게 하는 것은 순서와 문장이다.
여기 적힌 틀은 널리 알려진 발표·문서 방식(투자 유치 덱의 통상 순서, 결론부터 쓰는 피라미드 구조,
서술형 검토 문서, 한 장에 한 가지를 보여 주는 제품 발표)을 이 스킬의 템플릿에 맞춰 정리한 것이다.

## 1. 먼저 세 가지를 정한다

| 물음 | 정해지는 것 |
|---|---|
| 누가 듣는가 (투자자, 임원, 동료, 고객) | 순서와 말투 (아래 2, 3) |
| 듣고 나서 무엇을 하게 할 것인가 (투자, 승인, 구매, 합의) | 마지막 장. 여기서부터 거꾸로 짠다 |
| 몇 분인가 | 장 수. 한 장에 1~2분, 20분이면 10~12장 |

사용자가 이 셋을 말하지 않았고 자료만으로 알 수 없으면 **한 번만** 묻는다. 물을 수 없으면
"결론부터 말하는 보고"(`review`)로 짠다.

## 2. 듣는 사람별 순서

`new-deck.ps1 -Recipe <이름>` 이 아래 순서와 어울리는 테마로 프로젝트를 만든다. 순서는 `-Pages` 로 바꾼다.

### 투자 유치 — `pitch`

투자자는 하루에 여러 건을 본다. 첫 장에서 무엇을 하는 회사인지, 마지막 장에서 얼마를 왜 달라는지 알 수 있어야 한다.

| 장 | 템플릿 | 이 장이 답하는 물음 |
|---|---|---|
| 1 | `statement` | 한 문장으로 무엇을 하는 회사인가 |
| 2 | `problem` | 누가, 얼마나 자주, 얼마나 아픈가. 지금은 어떻게 버티는가 |
| 3 | `market` | 얼마나 큰가. **아래에서 위로** 센다(몇 곳 x 얼마 x 몇 달) |
| 4 | `features` | 제품이 실제로 무엇을 하는가 (말보다 눌러서 보여 준다) |
| 5 | `matrix` | 다른 방법과 무엇이 다른가. 축은 고객이 고르는 기준 |
| 6 | `trend` | 지금까지의 숫자. 가장 좋은 지표 하나를 크게, 기간과 기준을 함께 |
| 7 | `team` | 왜 이 사람들이 이 문제를 풀 수 있는가 |
| 8 | `ask` | 얼마를, 몇 개월 동안, 무엇을 증명하는 데 쓰는가 |
| 9 | `faq` | 반드시 나올 질문(단가, 이탈, 경쟁자의 대응) |

- "왜 지금인가"가 뚜렷하면 2장과 3장 사이에 `bignumber` 한 장으로 넣는다.
- 수익 구조가 단순하지 않으면 `pricing` 이나 `whatif`(가정을 바꿔 보는 단위 경제성)를 6장 뒤에 둔다.
- 숫자마다 출처와 기준 시점을 적는다. 추정은 추정이라고 쓴다. 지어낸 고객 후기는 쓰지 않는다.
- 장 수는 10장 안팎, 본문 글자는 뒤에서도 읽히는 크기(템플릿의 기본 크기)를 지킨다.

### 임원·의사결정 보고 — `review`, `report`

결론을 먼저 말하고 근거를 뒤에 둔다(답 → 이유 셋 → 자료). 바쁜 사람은 첫 두 장만 본다.

| 장 | 템플릿 | 내용 |
|---|---|---|
| 1 | `cover` | 제목이 곧 결론. 숫자 셋으로 지금 상태 |
| 2 | `agenda` | 오늘 볼 것과 **오늘 정할 것** |
| 3 | `kpi` | 핵심 지표 3~4개, 목표 대비 |
| 4 | `trend` | 벗어난 지표 하나와 그 이유 |
| 5 | `table` | 상세. 물으면 눌러서 보여 주는 용도 |
| 6 | `timeline` | 다음에 할 일과 날짜 |
| 7 | `compare` | 선택지와 추천안(기준을 바꿔도 추천이 유지되는지 보여 준다) |
| 8 | `closing` | 정할 일을 하나씩 확정 |

- 상황 → 문제 → 물음 → 답 순서로 도입을 쓰면 첫 장이 짧아진다(무슨 일이 있었고, 무엇이 문제이며, 그래서 무엇을 정해야 하는지).
- 글로 검토하는 조직(회의 전에 문서를 읽는 방식)이면 슬라이드보다 문서가 낫다. 그때는 덱을 3~4장(결론, 숫자, 선택지, 결정)으로 줄이고
  나머지는 문서에 둔다고 사용자에게 말한다.
- 새 일을 제안하는 보고는 "고객이 받게 될 것"을 먼저 쓴다: 완성됐을 때의 발표문 한 단락을 `statement` 에, 예상 질문을 `faq` 에 둔다.

### 제품 발표 — `keynote`

한 장에 한 가지만. 화면의 글자는 말하는 내용의 제목일 뿐이다.

| 장 | 템플릿 | 내용 |
|---|---|---|
| 1 | `cover` | 이름과 한 줄 |
| 2 | `statement` | 지금의 불편을 한 문장으로 |
| 3 | `bignumber` | 그 불편을 숫자 하나로 |
| 4 | `features` | 세 가지 이하의 기능을 눌러서 시연 |
| 5 | `quote` | 먼저 써 본 사람의 말 |
| 6 | `pricing` | 가격과 살 수 있는 날 |
| 7 | `closing` | 처음의 한 문장을 다시, 다음 행동 |

- 기능은 셋까지. 넷째부터는 기억되지 않는다.
- 숫자는 비교와 함께 말한다("18분 → 3시간").
- 어두운 테마(`midnight`, `ink`)는 큰 화면과 어두운 방에, 밝은 테마(`cupertino`, `snow`)는 밝은 회의실과 화면 공유에 맞다.

### 회의·워크숍 — `workshop`

같이 눌러 보며 정한다: `poll`(무엇이 중요한가) → `compare`(방안) → `whatif`(가정) → `closing`(확정).
투표 결과와 확정 스위치는 발표 자료 안에 남으므로 회의가 끝나면 그 파일이 곧 기록이 된다.

## 3. 문장

### 제목은 주장으로 쓴다

제목만 차례로 읽어도 이야기가 되어야 한다.

| 이렇게 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| 3분기 실적 현황 | 3분기 매출은 목표를 8% 넘었습니다 |
| 시장 규모 | 먼저 수도권 빵집 2,400곳부터 시작합니다 |
| 경쟁사 비교 | 정확하면서 바로 쓸 수 있는 자리는 비어 있습니다 |
| 향후 계획 | 11월 28일에 가을 메뉴 네 가지를 내놓습니다 |

### 숫자

- 단위, 기준 시점, 비교 대상을 붙인다: "재방문율 62.4% (9월, 전 분기보다 7.4%p 높음)".
- 형용사 대신 숫자: "크게 늘었다" → "두 배가 됐다".
- 한 장에 강조하는 숫자는 하나. 나머지는 작게 두거나 눌렀을 때 보이게 한다.
- 추정과 실적을 섞지 않는다. 섞어야 하면 색이나 꼬리표로 구분한다.

### 말투

- 합니다체로 통일하고 한 문장에 한 가지만 말한다. 두 줄을 넘으면 나눈다.
- 누가 언제 하는지 쓴다: "검토 예정" → "운영팀이 12월 5일까지 정합니다".
- 줄임말과 내부 용어는 처음 나올 때 풀어 쓰거나 `data-tip` 으로 설명을 단다.
- 꾸미는 말("혁신적인", "획기적인", "최적의")은 뺀다. 사실이 꾸밈보다 세다.
- 듣는 사람에 따라:

| 듣는 사람 | 말투 | 피할 것 |
|---|---|---|
| 투자자 | 단정하게, 숫자로. "~합니다", "~했습니다" | "~할 것으로 기대됩니다", 근거 없는 최상급 |
| 임원 | 결론과 필요한 결정을 먼저 | 경과를 시간 순서로 늘어놓기 |
| 동료·실무자 | 누가, 언제까지, 무엇을 | 주어 없는 문장 |
| 고객·일반 청중 | 쉬운 말, 받는 사람이 얻는 것 중심 | 내부 용어, 기능 이름 나열 |

### 글자 양

- 제목 한 줄(40자 안), 본문은 세 줄 이하. 더 필요하면 장을 나누거나 눌러서 펼치게(`faq`, 표의 상세) 한다.
- 화면에 쓴 문장을 그대로 읽지 않는다. 읽을 대본은 발표자 메모에 둔다.

## 4. 눌러 볼 수 있다는 점을 이야기에 쓴다

| 상황 | 쓰는 것 |
|---|---|
| 한 번에 다 보이면 앞질러 읽는다 | `ph-frag`: "다음"을 누를 때마다 하나씩 |
| "그 숫자는 어떻게 나왔나요?" | `market` 의 셈법, `table` 의 줄 상세, `data-tip` 설명 |
| "가정이 다르면요?" | `whatif`, `ask` 의 막대 |
| 질문이 앞 장 얘기다 | "다음" 단추나 쪽 번호를 **길게 눌러** 슬라이드 고르기 |
| 뒤에서 차트가 안 보인다 | `data-zoom`: 눌러서 크게 |
| 회의 중에 문구가 바뀐다 | 연필(편집): 그 자리에서 글자를 고치고 저장 |
| 강조할 곳을 짚는다 | 펜, 마우스를 따라다니는 고리(`PH.ring`) |
| 의견이 갈린다 | `poll` 로 그 자리에서 센다 |
| 시간이 정해져 있다 | `PH.timer` |

움직임은 뜻이 있을 때만 쓴다. 숫자가 올라가는 것, 선이 그려지는 것은 "변화"를 말할 때 어울리고, 모든 장에 넣으면 방해가 된다.

## 5. 테마 고르기

| 자리 | 어울리는 테마 |
|---|---|
| 투자 유치, 핀테크·기업용 서비스 | `indigo`, `geist`, `snow` |
| 제품 발표, 소비자 제품 | `cupertino`, `seoul`, `midnight` |
| 사내 보고, 운영 현황 | `cobalt`, `fluent`, `cloudscape`, `carbon` |
| 개발자 대상, 기술 발표 | `primer`, `primer-dark`, `geist`, `carbon-dark` |
| 읽는 글에 가까운 발표, 공익·환경 | `paper`, `forest`, `ink` |
| 구글 계열 도구에 익숙한 청중 | `material` |

회사 고유의 색과 글꼴이 있으면 가까운 테마 파일을 복사해 값만 바꾼다(`references/kit.md` 의 "테마").
이름이 붙은 테마는 각 회사가 공개한 디자인 값이나 널리 알려진 화면 느낌을 따른 것이지 그 회사의 공식 자료가 아니다.
덱에 그 회사의 로고나 이름을 넣어 공식 자료처럼 보이게 하지 않는다.

## 6. 만들기 전 점검

1. 제목만 이어 읽어도 이야기가 되는가.
2. 마지막 장이 "감사합니다"가 아니라 요청이나 다음 행동인가.
3. 장마다 주장이 하나인가. 둘이면 나눈다.
4. 숫자마다 단위·시점·출처가 있는가. 예시 숫자가 남아 있지 않은가(템플릿의 숫자는 모두 지어낸 것이다).
5. 5초만 보고도 그 장의 요점을 말할 수 있는가.
6. 강조색은 한 장에 한 곳인가.
7. 눌러야만 보이는 내용 가운데 꼭 전해야 하는 것은 없는가(정지 그림과 인쇄에는 처음 상태만 나온다).
